# 阶段健康检查与规则复查

本流程由开发 AI 在显式调用本 Skill 后，或项目已采纳并映射本流程的授权任务中执行；生效边界按[lifecycle.md](lifecycle.md#模式与生效边界)，不自动加载整个Skill。用户只要求检查时，范围仅为读取、扫描与报告；修复按当前写入授权执行。结果保存在对应 TASK 文件正文，较大证据作为任务附件；治理结果沿下方统一呈现格式，不新增独立报告台账或后台调度承诺。

## 项目综合治理入口

“项目综合治理”及其检查对象“治理体系”的含义按[机制术语表](terminology.md#2-产品规则与开发流程)，本节维护方案与执行的衔接。

用户要求“治理项目”“项目综合治理”等整合工作时，先形成与项目现状相匹配的完整实施方案，再沿授权执行。仅要求专项检查、治理规则更新或阶段复盘时，仍使用对应入口；讨论这些词不构成执行请求。需要加载Skill时显式使用`$ai-sdlc`，已采纳项目规则按本页开头的生效边界执行；本入口是任务意图，不是新增CLI命令。

先低成本读取项目入口、现行规则、任务/待办、相关差异和既有检查证据，按[执行力度建议](#执行力度建议)判断检查范围及证据复用。范围优先采用用户指定对象；未指定时结合项目现状界定并说明，仍有影响范围或授权的关键歧义时再询问。明确要求完整项目或阶段治理时保留该范围，不能自行换成局部扫描。

向用户简要说明整合方案，并在实施任务正文的计划章节维护；跨任务依赖复杂时按[lifecycle的阶段计划规则](lifecycle.md#跨任务安排与发布信息归属)承载共同安排。仅咨询或仅要求方案时按请求交付方案，不自动建立实施任务或执行修改。方案至少覆盖以下内容，相关依据直接引用，简单范围可简写：

1. **范围与完成标准**：目标、对象、现行依据与保护范围；所选基础专项及实验、UX、安全适用性，已有证据、待补证据和排除理由；按[项目裁剪](#项目裁剪与检查力度)确定尺度，完整性主题沿设计专项DS-07映射；范围包含运行或交付时核对[部署运行要求](#部署运行要求)。完整项目或阶段治理沿[触发与选择](#触发与选择)保留五类基础专项及适用条件专项，局部治理说明选择依据；完整范围不等于逐行穷举或全量测试。
2. **步骤与依赖**：沿[必需流程与顺序](#必需流程与顺序)分别安排调查、修改及结论收口，衔接专项依赖、问题归因与处置、主要修改后的遗漏核对、复验及治理体系回顾。说明哪些决定/修改是后项前提，哪些变化会重开已检查项，注明检查点、可并行工作及需要人的决定，复用任务正文与已有关系地图。全面治理在相关处置与复验完成后、最终交付核对前安排[项目导览页](#项目导览页)；发现影响后续安排时，在继续依赖步骤前更新方案。
3. **成本与交付**：验证级别及执行前确切命令、时间或预算边界、暂停与恢复条件，以及结果入口、证据和剩余事项的交付方式。所需环境或预算不足时保留未完成和影响，不以缩小事后口径取得通过。

综合治理必须包含治理体系自身的回顾和是否需要更新的判断，按以下时机融入同一方案：

- **检查前**：沿[治理体系与项目实际](#治理体系与项目实际)定位现行规则、入口、已采用模板、配置和实际流程；结合历史发现及暂缓条件判断依据是否有效、是否足以开展本次工作。
- **检查与修复中**：把规则缺失、冲突、冗余、职责或流程衔接问题与实现缺陷区分，核对根因及受影响消费者。需改变后续执行依据时，先按授权更新唯一正文及相关入口、模板/配置或项目映射，再依赖新规则实施；不把更新全部留到收尾，也不把所有问题都归因于缺规则。
- **收尾时**：沿[阶段回顾与治理更新](#阶段回顾与治理更新入口)和[主动复查](#主动复查)核对实际结果、偏差及可复用经验，记录规则保留、修改或退役的依据，验证已更新规则与实际执行的一致性。无必要修改时说明依据并保留现状；后续与未决决定归现有任务/待办。

方案形成后直接推进已有授权内的工作，不新增统一审批；只读范围只交付发现与建议，超出授权的产品含义、权限或重大变更仍沿既有决定边界处理。复用本页检查底线、发现分级、独立复核触发和完成条件，不另建一套专项或强制全部更新治理文件。收尾分别报告调查、修复、治理规则处置及验证状态；有未闭合必需项时只交付部分结果，不能把调查完成写成综合治理通过。

### 治理结果统一呈现

治理交付在对话摘要和对应任务正文的“治理结果”小节中，先用一句简短的开场说明交代本次做了什么、针对什么对象及目的；必要时点明范围。开场不寒暄、不复述请求、不提前重复完成状态或结果，随后按同一顺序呈现以下五项。详细发现与验证证据仍在任务原有记录或附件维护，摘要引用即可，不重复复制执行流水；不强制新增独立报告文件。多任务治理在主任务汇总并链接子任务，不另立状态来源。

1. **治理结论**：完成／部分完成，以及本次实际覆盖范围。仅检查或仅方案时明确写“检查完成”或“方案完成”，不能写成综合治理完成；必需项未闭合时写部分完成。
2. **主要结果**：关键发现、已完成修复，以及治理规则修改、保留或退役及其理由。区分发现与实际处置，优先保留影响用户判断的结果；无发现或无需修改时据实说明。
3. **验证情况**：已验证的内容和结果、未验证的内容及原因，链接必要证据。检查通过不代替人工验收，也不证明范围外效果。
4. **剩余事项**：未完成项、残余风险、待人的决定及下一步，注明必要的责任归属或触发条件；无则写“无”。范围内必需项不能转为后续事项而宣称完成。
5. **交付文件**：链接任务记录、必要证据和适用的项目导览等实际产物。仅列真实存在的文件；全面治理的HTML与页面验证仍按下节要求，局部治理不因此新增导览。

开场说明不另编号，五项标签与顺序固定，篇幅按任务规模裁剪，小任务每项一句即可。对话与落盘结果应表达一致的结论、验证边界和剩余事项，任务状态继续由原任务机制维护。只读或仅方案授权不因本格式获得写文件权限：对话沿用开场说明及五项，交付文件项说明未落盘及原因；有明确文档写入授权时才保存。

### 部署运行要求

治理范围包含系统运行或交付时，核对被治理系统部署后的环境要求及其依据，不能以开发机配置、构建成功或工具自身的要求代替。正文复用README运行章节或现有运行说明；复杂时按[目录职责](project-layout.md)拆至development，不新增必建文件。只读治理记录缺口，已授权修复时维护唯一正文。

从实际功能、部署方式和负载识别影响运行的资源与约束；下列维度仅为示例，不是完整或必填清单，可按项目增删，不以填完示例代替完整性判断。按实际部署形态核对操作系统及版本、CPU架构、运行时/容器与必要服务依赖，适用的CPU、内存、磁盘容量及增长、GPU/显存及驱动或计算运行库、网络和权限条件。无关示例可省略；存在适用性疑问时说明依据，不为凑表引入硬件要求；外部模型API不等于本机需要GPU。开发/构建与部署运行条件分开，托管服务记录可控配置及外部依赖，不猜测供应商底层硬件。

区分已确认最低要求、推荐配置、实际验证配置；配置绑定版本、部署方式和代表负载（如并发、数据量、模型及精度），引用约束来源或实际证据。没有依据的最低值标为待验证，单机成功不证明最低配置或全部支持范围。缺口注明影响和下一动作；影响当前验收时沿现行验证规则处置，不自动购买资源、部署或启动高成本基准。实际运行验证沿[验证健康VH-05](validation-health.md)，容量验证沿[性能容量与运行费用](verification.md#性能容量与运行费用)。

运行依赖、支持范围、部署方式或负载假设变化时，最晚在依赖新条件前维护正文并按影响复验。导览仅在既定刷新时机摘要影响使用的关键门槛并链接该正文，不另维护一份配置表。

### 项目导览页

项目导览页帮助项目所有者理解项目目标、使用方式、主要组成、重要取舍及能力边界，是带核对时间和内容身份的阅读快照，不是另一套规则或实时状态来源。

**时机与授权。** 已授权实施的全面项目治理，在检查、授权内修复、治理体系回顾与按需更新及复验完成后，必须建立或刷新 HTML 项目导览，核对页面后作为治理交付的一部分。缺少 HTML 页面或所需页面验证时，记录未完成及下一动作，不得宣称全面项目治理完成。首次建立，后续复用刷新，不要求用户另行提醒。日常任务、局部治理、单独阶段/专项检查及首次接入不默认触发；用户单独请求生成或刷新时，也可在该授权范围执行。仅检查、仅方案或只读请求不写页面；实际生成、更新和发布各沿当前授权，不由页面内容扩权。

**承载与内容。** HTML 是必需的展示形式，已有 Markdown 文件及其内容维护职责保留，不因新增 HTML 而删除或迁移。优先复用项目已有 HTML 介绍页或文档站的导览页面；无合适页面时建立离线 HTML，默认位置为 docs/project-guide.html，已有布局可映射到等效位置。存在 Markdown 导览时，以该文件为唯一导览内容源，HTML 必须由它生成；文档站沿用其现有内容源和构建方式。没有合适的导览内容源时，可建立 docs/project-guide.md 或项目等效源文件再生成 HTML。正文、图定义及必要说明在同一内容源或由其明确引用的受控源资产维护，修改源后重新生成HTML，不独立编辑两份正文；生成方法及源到展示页的对应归项目现有运行/构建说明，不要求新 CLI 或服务。README 文字章节或 Markdown 文件不能单独替代 HTML 交付，README 链接实际 HTML 入口。内容源与展示页分工明确，规则和详细状态仍在原维护位置，不建立第二套现行正文或 Wiki 服务。默认阅读主线为：目标与边界 → 核心能力 → 主流程 → 架构与协作 → 关键设计取舍 → 当前限制，参考[导览模板](../assets/templates/optional/docs/project-guide.md)。简单内容可以合并呈现，但仍回答这六类问题，进一步阅读附真实来源。核心能力按用户能完成的事情组织；主流程说明用户完成核心任务的入口、必要前提、主要步骤、可观察结果、关键分支和失败出口，不用模块调用链替代。流程复杂时用主流程图，跨角色时可用泳道图，简单路径可用有序步骤；数据流、状态、时序和部署图仅在影响理解时补充，不强制凑齐。面向项目读者解释，不能只堆代码路径或治理记录。已有文档站沿用其技术栈；无现成页面时离线 HTML 即可，不强制框架、交互、联网、账号或部署。

**工程理解与接手。** 在保留上述产品视角及基础图解的同时，让读者定位：关键技术执行路径、模块/接口/数据/失败恢复及其依据；已确认开发安排、目标与依赖；当前范围内已实现、已验证、已交付的区别；已知问题、阻塞及待人的决定；下一步、条件待办和暂缓项的重新进入条件。按实际资料在现有板块或工程态势章节组织，不强制每项独立成页或另建roadmap/问题台账。没有已确认计划时直接说明；可选建议不能画成批准路线，不用任务数量生成无依据的总体百分比。摘要注明截至日期和对象，链接实时状态与原任务/证据；缺资料保留未知，不把测试成功、任务completed、版本号或图上标记互相替代。

复杂关系可提供节点详情、上下游/路径聚焦和实现/设计/检查/任务来源回查，先保持主线可读，再按需展开；完整代码关系图用于深入调查，不要求首页展示全量。已有实现优先复用。可选[随包工程导览工具](cli.md#可选工程导览工具)提供生成、明确来源身份和已有关系查询；使用者编写经过核对的图定义，工具不自动发现依赖或证明关系完整/语义正确。图中观察、推断及待核实分别表达；来源文件/行号存在只支持可定位和内容身份，不代替实际关系审阅。同源与事实归属沿本节“承载与内容”及“事实与范围”。

**HTML 格式底线。** 页面用于项目阅读与定位，优先沿用现有设计及文档站。新页面采用简单一致的排版，具体字体、配色、字号、行距和宽度由项目按目标环境选择，不设通用数值或强制框架。

- **结构。** 设置明确的页面标题和一个正文主标题，核心板块使用有序的标题层级；长页面提供目录或锚点导航。页首快照信息按本节“事实与范围”，进一步阅读指向实际来源。
- **阅读。** 正文行宽、字号、行距及前景/背景搭配在目标环境可读；标题、正文、代码、表格和图示可区分。中文及字体回退、长文本、URL、代码和宽表格不造成遮挡、截断或整页布局破坏；需要横向查看的局部内容提供可用的查看方式，不靠隐藏溢出丢弃信息。
- **使用。** 链接、目录和已有控件可操作，可聚焦对象有可见键盘焦点；图示有标题及必要文字解释，关系不只靠颜色区分。离线 HTML 的正文、图示和基本导航可直接打开，不依赖联网资源加载；在线文档站沿用其实际交付形态。只核对项目支持环境，不自增移动端、动画或交互要求。

**来源与缺口。** 六部分复用项目实际维护位置：目标/范围、核心能力和用户流程优先核对需求及使用说明，能力现状再对照实现/验证；架构协作核对设计或等效说明及相关实现；取舍引用任务或决策记录；限制核对状态、待办和验证证据。存在模板或映射不代表资料齐备，尤其不能把零散需求直接当作完整主流程。来源不足时先做范围内的低成本核对，区分观察到的实现与已确认意图；无法确认的标为待核实及其影响，需要维护现行依据时沿原授权更新唯一正文，不只在导览里编造事实。不要求六份独立源文档，不强制新建架构/决策记录，也不借补齐导览扩大为业务重设计。

**事实与范围。** 页首注明核对日期、对应项目版本及可定位内容（提交、任务差异或项目等效标识）、本次刷新来源和范围；这些信息只维护一处，各展示位置从同一来源派生。日期以真实核对为准，不以改时间戳冒充刷新。明确页面不是实时状态。需求、设计、任务及证据仍在原处维护，重要结论附真实来源链接；未证实描述标为待核实，设计意图不能写成已实现或已验证。简述能力进展即可，详细任务状态和测试计数引用现有入口。缺证据、治理中断或有未闭合必需项时不得把页面标为治理完成；若已授权交付部分结果，可更新已核实部分并标明未完成范围，否则保留原快照并在任务记录下一动作。不补造首次页面的治理历史。

**浏览器预览入口。** HTML离线交付与自动浏览器验收分开。验收前核对所用工具的协议支持和实际权限，不以尝试被禁止的协议作探测；自动验收采用获准的HTTP/HTTPS入口，不默认打开`file://`。优先复用项目已有开发服务器；无合适入口时，可使用[受限导览预览工具](cli.md#受限导览预览)：仅回环地址、显式页面及必要资源、无目录浏览和写入，验收后停止。先核对预览快照与待验收文件内容身份，文件变化须重启快照并只复验受影响项。已有安全拒绝时停止该访问路径，不自动换协议、端口或工具重试；正常预览流程不构成解除拒绝的许可。无获准入口时保留浏览器验收未完成，可由用户手动打开离线HTML按同一验收项核对并记录人工结果；静态检查、人工结果与AI浏览器结果分别记录。HTTP预览通过不证明`file://`离线运行通过，也不解除工具限制。

**核对与维护。** 对照本轮最终实际结果检查文字、来源链接、日期/身份和限制；实际 HTML 按项目验证来源核对上述格式底线、两个基础图解视角的实际呈现、受影响布局、导航及存在的交互；保留的 Markdown 内容源核对结构、链接；追查实际生成来源与方法，核对 HTML 对应当前内容源、无独立修改导致的漂移。Markdown 完整或构建成功不能代替实际页面验证。页面若揭示新缺陷，回到对应处置，待相关复验后修正页面再交付。结果与未完成项记入原治理任务，README链接实际入口；不新增台账、状态字段、后台监控、来源指纹或逐任务更新拦截。日常维护现行事实来源即可，快照允许落后；下一次全面治理或明确刷新请求再更新。该时机适用于导览快照，不改变现行规则、使用说明和状态源原有的及时维护义务。

**图解对象与关系。** HTML 导览必须呈现以下两个基础图解视角，可分别绘制或在同一图组中清楚分区；简单项目可以简化，但不凭空增加角色、模块或依赖：

1. **使用与协作图。** 从外部使用视角说明用户或调用方、系统及适用的外部参与者，表达关键入口、输入/结果及工作或反馈关系；不能默认把开发 AI 的工作流当作被治理产品的用户流程。
2. **内部结构与依赖图。** 说明系统边界、主要组成及真实依赖，按实际需要表达调用、读写/数据存储及外部依赖，区分固定与可选关系；不只列目录或组件名称。

两个基础视角不能证明所有重要关系已讲清。多步骤及关键分支/失败出口需要图解时补主流程图；异步、重试或状态变化影响理解时补时序/状态图；数据去向、权限或部署关系影响理解时补数据流/部署图。依据具体理解缺口选择，不固定追加图数。绘图前明确读者问题、解释对象和视角，多个必要视角互补，不能因替换图而遗漏已确认内容。图的源维护沿本节“承载与内容”；实际页面必须显示图，未渲染的图代码不能替代图示交付。问题明确时由开发AI选择，歧义会改变结果且现有依据不足时再询问。重要的调用、读写和控制关系沿入口追到实际执行或配置位置，区分请求者、执行者和数据存储，以及固定依赖与可选能力；记录影响理解的条件和未知，复用现有来源链接或任务材料，不要求每个节点建立台账。引用存在不能证明关系含义正确，图文语义与布局/交互分别核对。

## 检查底线

检查清单与标准流程构成最低执行要求。所选专项的全部条目必须逐项处置，模型可以增加维度、改进工具与调查深度，不能以自己的偏好、成本判断或新增检查替代必需项。只选择部分专项可以成立，但结论须明确范围，不能称为完整阶段健康检查。

“适用条件”不成立才可记不适用，必须提供项目事实与依据。工具缺失、环境不可用、时间不足、依据矛盾或检查对象不明均记未完成，并列明影响和下一动作，不能作为不适用。必需项不能静默省略。新发现说明范围不足时，应扩展覆盖或报告限制，不能通过缩小事后口径消除缺口。

模型可提出底线修订建议；现行规则存在冲突时先定位其优先级与负责位置。按照项目已有授权确认或维护规则后才能依赖新规则，保留变更原因和前后依据。不得为本次通过自行豁免、降低要求或把未知写成通过。

## 结果底线与方法选择

必需项约束风险覆盖、结果及支持结论的证据。开发 AI 按项目选择工具、实现、调查深度及无依赖步骤的顺序，可以合并调查并复用仍有效的证据；通常无需另行批准方法选择。示例不是指定实现或必做步骤，替代方法须支持同一要求，不能通过换方法跳过适用风险。项目已有明确契约、验证要求和授权边界仍有效。

检查维度与场景穷举分开：按变化和风险选择代表模块、边界数据及环境，记录覆盖与盲区；不默认穷举页面、状态、设备或故障的全部组合。覆盖不足以支持结论时补查或限定结论，不事后缩小范围掩盖必需缺口。

对“不存在、未发生、不再使用”等否定结论，先核对检索范围、排除项和方法有效性。删除、历史定案等重要决定结合适用的独立证据交叉核对，不规定固定来源数量；证据不全时写“在已查范围内未发现”。读取历史经验时核对后续修正，不能将已被替代的决定恢复为现行要求。

## 项目裁剪与检查力度

检查覆盖、实现深度和验证强度分别决定。开发AI先核对失败后果与可恢复性、独立变化/失败环节和并发/共享状态、实际用户/数据/负载规模、交付阶段及既有证据，不按代码行数、用户少或加权总分豁免高影响风险。目标、硬约束和既有决定有效；超出授权的取舍沿[lifecycle主动询问](lifecycle.md#需要人的决定)。

| 参考力度 | 典型条件 | 合理起点 |
|---|---|---|
| 轻量 | 单人短时运行、数据可重建、失败低成本可恢复 | 清楚边界、默认值和错误反馈；核对关键成功/失败路径 |
| 常规 | 持续使用、重要持久数据、多人协作或外部依赖 | 明确配置、状态、恢复及迁移规则；按声明验证真实边界 |
| 加强 | 高影响权限/数据、不可逆副作用、复杂并发或较高服务承诺 | 明确故障模型、隔离和恢复目标；针对关键风险验证并发、故障及实际环境 |

这三档是参考，不是评分、固定套件或全任务必填字段；项目可在不同领域采用不同力度。小工具的密钥保护可加强而其余仍轻量，大项目的局部文案修改不因项目规模升级全量。高影响风险不能被其他简单条件抵消。原型可暂缓未承诺的生产能力，但真实敏感数据和不可逆动作的保护仍按实际后果适用。

完整检查通过DS-07判断声明范围内全部主题的适用性；主题需要考虑不等于必须建设组件。日常局部任务只重核受影响主题；正式选择专项后仍处置其全部ID。未实现不等于不适用；已有机制满足要求时复用有效证据，平台保障核对其真实边界；适用但未满足记录缺口，不用“项目小”或预算不足写不适用。

同时检查必要性与充分性：新增机制应说明它保护的当前或已确认近期场景，以及更简单办法为什么不足；现有方案应说明关键失败后必要结果如何保持及其证据。配置文件、清楚错误、可靠重建或现有平台可满足要求，不强制配置中心、日志平台、数据库或分布式架构。已有项目要求仍须满足，不能借裁剪降底线。

按阶段暂缓仅适用于不影响当前交付承诺的事项，在现有任务/待办记录依据、责任和重新检查条件，如开始保存重要数据、增加写入者、开放外部访问或持续服务；接受风险超出授权时先询问。接手、阶段转换和相关变化时检查这些条件。裁剪依据复用任务正文/证据，简单情况一句话，不新增评分表、成熟度台账或审批。

## 独立上下文复核

改动涉及规范冲突的取舍、需求或验收含义、验证器或交付判定的规则/实现，或跨模块关键行为边界时，先判断失败后果、可恢复性、判断不确定性及已有保护。存在高影响或难恢复后果、关键含义/授权冲突未决、当前证据难以排除的关键判断错误，或项目已有明确独立审阅义务时，交付前安排独立上下文复核；不只凭文件类别或涉及上述主题就强制升级。影响明确、局部可逆且有效验证和差异审阅足以支持结论时，可由当前执行AI完成语义自查，在原任务说明依据，不冒充独立复核。普通低风险修改及未改含义的文字、格式或链接不默认触发。复核覆盖相关判断及消费者，不要求每个专项各开一个复核者，也不自动扩大测试范围。

具备可用且获准的子 agent 工具时，优先使用不继承实施对话历史的子 agent；已有独立审阅者能覆盖同一范围时可复用。向其提供用户目标、授权、已确认决定、实际差异、现行规则和实现入口、原始验证证据，允许按需追查来源；不以实施者的推断、预期答案或成功摘要代替这些材料。隔离的是实施判断，不是必要事实或授权。默认只读复核，不扩大原任务的修改或外部操作权限。

复核者从差异追到依据和消费者，核对重要选择回答的具体问题、适用范围及其授权；修改文件的权限不自动包含改变其中业务含义的权限，已有有效授权直接复用。规范冲突先核对是否约束同一问题和范围，再说明采用的解释及来源，不能只统一文字或以现有实现自证需求。输出覆盖、发现的位置/依据/影响及未证明事项，复用任务正文或附件。实施者按证据处理分歧并修正，受影响结论在修正后重新核对；不以人数或一致意见代替依据。已有独立复核仍适用时复用，不递归要求复核每份复核报告。

无法取得所需独立复核时（如工具不可用且无可复用审阅、委派不获准或必要材料缺失），记录独立复核未完成及影响，可继续不依赖其结论的工作；在所需复核补齐前，不宣称受影响交付范围完成。同一实施上下文自查不能冒充独立复核，独立复核也不代替所需测试、人工验收或发布授权。

## 架构与流程走查入口

方法唯一正文归[设计专项的架构与流程走查](design-conformance.md#架构与流程走查)，复用DS职责及本页证据、发现处置和成本规则。

- **单独走查**：用户要求“架构与流程走查”、梳理模块输入输出并核对设计/实现或评估设计合理性时，按指定系统、子系统或关键流程执行；未指定时先依据目标、差异与既有证据界定并说明。只检查请求交付模型、发现和建议，修复沿当前授权。可作局部方法检查，不因此选全部专项；明确请求正式设计专项时仍执行其全部条目。
- **全面治理**：在已有设计专项中安排本方法或复用仍有效的走查证据，与其他专项共享调查；保留已声明范围和全部必需条目，按风险选择关系核对深度。检查所用模型可在修复后支持既有导览流程，全面治理HTML义务仍沿原入口，不新增第二份导览内容源。
- **变化与风险触发**：首次需要架构基线且缺可信模型、跨模块集成、职责/接口/共享状态变化或重复系统性故障时，按当前任务影响建立或更新相关关系并走查。已有可信模型直接复用；日常小修改仅查受影响部分，是否正式选择专项仍沿下节判断，不默认全系统重画或全量测试。

范围、可复用依据、完成标准及必要成本边界写原任务；先有界检查关键流程，再因具体缺口补查。发现并验证一部分有价值问题可形成收益，无发现也可完成约定调查；模型覆盖、调查完成及系统健康结论分别报告。

## 遗留与废弃物治理入口

用户要求治理废弃代码、死代码、孤立/多余文件或项目残留时，按所请求项目、模块或目录建立有界任务，复用[代码健康的处置方法](code-health.md#遗留与废弃物处置)；检查不限于重构来源。未明确范围时，依据现行入口、变化、既有发现及有效证据界定并说明；只要求检查时交付候选、判断依据和建议，授权清理时推进可确认的可逆处置，超出范围或改变兼容/保留承诺沿原决定边界处理。

调查复用CH-01定位对象、CH-02核对用途和废弃依据、CH-06验证处置；目录与生成/归档对象联用[目录清理入口](project-layout.md#目录检查与清理入口)，依赖契约或数据保留疑点按实际影响联查设计/验证职责，共享证据只记录一次。可以单独按本方法治理，不因此选择全部代码健康条目或五类基础专项；明确要求正式代码健康专项时，仍逐项处置该专项全部ID。全面治理和阶段检查沿已有选择入口纳入相关调查，不增加第六类基础专项。

完成需有范围与覆盖依据、删除/保留/待核实的处置理由及受影响行为验证；待核实或未覆盖部分明确限制，当前验收依赖的缺口未闭合只能部分交付。没有确认可删对象也可以完成调查，不设清零或删除数量要求。沿现有任务记录，不新增自动删除器、后台扫描或全量测试义务。

## 触发与选择

- 日常任务只整理授权范围内的局部问题，不自动运行全部专项。
- 选择正式专项前，先判断当前受影响核对与定向验证能否支持任务验收。修改规则、模板、UI或新增工具本身不等于阶段结束、跨模块集成或正式专项请求；不能仅为使收尾“完整”主动选择多类专项。已有明确阶段、风险或专项触发仍须执行。普通局部任务可引用相关条目指导检查，但不据此声明整个专项通过，也不创建正式扫描覆盖块。
- 确需正式专项时，在实施前注明触发、对象及现有证据不能覆盖的缺口；已有任务范围与验证声明能表达时直接复用，不新增表格。所选专项仍按全部条目处置，共享证据合并引用；具有相同事实依据的不适用条目可合并说明并保留全部ID，不逐项重写相同理由。环境缺失或必需检查未完成不能合并成不适用。
- 阶段结束、跨模块集成或进入依赖当前结果的下一阶段前，检查本阶段及消费者；完整阶段检查采用下列五类基础专项，并判断实验、UX、安全三个条件专项在本阶段范围是否适用，适用者纳入必需范围。仅某一方面发生变化时，可选择受影响专项并说明依据。
- 首次建立全项目健康基线、重要架构调整后、反复跨模块故障，或阶段检查发现问题扩散时，评估全项目扫描。记录模块清单、风险、覆盖方式与预算；不能仅凭代码行数宣称需要全量。
- 模型、工具、规则重大变化或漏检误拦时，复查其影响的规则与检查方式。未运行的后台不能自动触发；接手时核对已有阶段安排。

| 实验与评价 | [experiment-review.md](experiment-review.md) | 本次需要依据实验作能力、路线或收益判断；或实验/评价方法有实质变化。仅使用模型、普通回归或无关改动不触发 |
| 用户体验 | [ux-review.md](ux-review.md) | 本次界面/交互变化、体验故障或阶段范围包含用户界面。局部任务只查相关流程，不因项目有界面就全站扫描 |

日常局部检查按影响选择；已有条件专项证据仍有效时复用，不因跨入新阶段重复运行。完整检查的适用性判断写任务正文；不适用按事实说明，缺环境仍为未完成。

### 治理体系与项目实际

完整阶段检查将阶段范围及相关消费者的治理体系纳入对象；用户明确要求项目治理体系整体扫描时，覆盖其现行规则、入口、模板/生成源、实际配置及执行流程，不只扫描业务源码。治理回顾或局部修改仍按影响选择，不能仅因项目有治理文件就升级为整体扫描。先定位项目实际采用的来源和例外，未采用的可选模板、上游Skill及历史材料仅在存在依赖或解释需要时追查，不自动要求同步最新版。

复用现有条目分工：DC-01/DC-05核对依据、冲突与重复正文；DS-02/DS-03核对职责、流程衔接和非必要步骤；DC-03、DS-01及VH-01/VH-04核对治理要求与实际代码、配置、命令和证据的双向对应。既从规则追查执行落点，也从实际流程反查依据、遗漏及已确认演进；没有自动执行器的项目以真实执行记录核对，不要求为扫描新建工具。正式选择专项仍处置其全部条目，共享发现和证据只记录一次。

范围内的相关文件与执行关系写入现有任务覆盖记录，区分体系内部一致性、与项目实际符合性及尚未验证的行为。冗余以重复维护、冲突或具体理解/执行成本为依据；入口摘要、必要提示、合规留存和有理由的重复可保留，不以“零重复”为通过标准。无收益的判断须有使用或依赖依据，材料不足记待核实；修复沿现有分级与授权，不因扫描自动删除历史、放宽验收或迁移项目。

### 执行力度建议

用户发起健康扫描/回顾或上述触发成立时，先低成本核对最近相关检查的对象与覆盖、此后实际变化、证据有效性、未闭合发现和新风险。说明推荐力度、依据、覆盖、可复用证据与升级条件：无新增相关信息且证据充分时可建议暂缓重复扫描；局部影响明确时增量核对；跨模块退化或风险边界变化时选择相关专项；缺可信基线、覆盖不足或明确阶段要求时安排有界基线/阶段检查。没有历史证据不能据此建议跳过。

不按间隔短或代码改动少直接减量：权限一行变化、新漏洞信息、运行配置/依赖环境变化均可能改变风险；复盘也可因提醒、返工或恢复困难而有价值。用户笼统请求时，说明依据后按适当力度执行；明确要求完整扫描时尊重范围，不自行改为抽样或取消，可复用仍支持该范围的证据。建议不能豁免现行必需检查，预算不足则报告限制。日常影响核对不自称专项通过；正式选择专项时仍处置其全部条目。

### 累积变化与既有义务

阶段检查沿最近相关检查或可定位的阶段起点，查看累积差异、反复修改热点、既有发现及暂缓事项。比较职责重复、例外分支、修改扩散、缺陷复发、兼容路径及UX变体等与当前对象相关的信号；代码健康检查按CH-02/CH-06核对重构、功能下线及试验/调试等累积的失效代码和关联文件残留，处置方法归[遗留与废弃物处置](code-health.md#遗留与废弃物处置)。无历史基线时建立当前起点，不能补造趋势。指标只提供线索，结合具体行为、理解/修改成本及可逆性决定保留、简化或重构，不以行数或整洁偏好自动整改。

接受临时方案或例外时，在现有任务/决定或唯一待办中保留理由、适用范围、责任、退出或复查条件；普通局部选择不另建决定文件。接手、选择下一任务及触及相关对象时核对条件，成立后决定继续保留、修复、迁移或退役，依据进入原维护位置。当前验收依赖的问题不能转入待办；范围外改善不得自动扩大任务。阶段检查结果仍归任务，status仅按需链接最近相关检查及下一检查点，不复制覆盖和发现状态。

## 必需流程与顺序

本节维护治理检查中的专项编排、跨项回返和统一收口。通用任务修改前后核对、反馈与授权沿[lifecycle](lifecycle.md#共同任务流程)，验证力度、证据失效及复用沿[verification](verification.md)，具体调查与处置方法沿各专项。条目编号用于记录身份，阶段用于表达依赖；调查、判定和修复可按模块或流程分段推进，无依赖工作可以并行，保留所选专项全部适用条目的处置义务。局部检查只应用相关关系，不因此扩成全面治理。

1. **固定基线与范围。** 记录任务授权、源码标识及未提交差异、现行需求和规则版本、所选专项、模块或用户流程清单、预算、完成标准与保护对象。明确工具扫描、关系核对、深入审查各覆盖什么；生成物、第三方代码等排除对象也记录。全项目扫描不自动等于逐行审查。
2. **核对前提与验证条件。** 定位本次判断依赖的现行要求、概念、质量目标及未决选择；必要实验、用户任务和安全约束按其依赖参与，不留到依赖操作之后。完整阶段检查先做VH-01、VH-04初查；在依赖测试或探针支持修改判断前，沿lifecycle的反馈要求及相关VH-02/VH-03核对本次所依赖的覆盖和有效性，可复用已有充分证据，不因此先做完整验证健康专项。缺证据可以继续独立静态调查，不得作依赖该证据的行为通过结论；修复前确定相应验证路径。
3. **执行专项。** 推荐以术语体系、交付一致性、设计完整性与一致性、代码健康、验证健康组织调查；适用的条件专项与相关调查合并，遵循各专项的必要依赖。表格是推荐组织顺序，不是固定串行流水线。现行依据核对必须早于一致性判定；术语先核对词表增删改，按有效词表扫描后才能依赖其修复；涉及概念含义的其他专项结论须先解决对应术语依据；证据收集早于结论；影响分析早于修复；修复后复验早于通过。没有这些依赖的调查由开发 AI 自行调整；影响覆盖或结论的安排说明理由，不为普通方法选择追加记录，不省略适用必需项。严重故障可先止损，沿用事故授权，之后补齐剩余检查。
4. **汇总与判定。** 每个条目记录覆盖及结果，重复症状归并为一个发现，关联原条目和证据。区分实现缺陷、已确认演进、过期文档、依据未决和一般改进；按下述分级确定必需处置。不能机械把代码恢复到过期设计。
5. **按依赖修复与复验。** 同一依赖链内，先处置会改变后续依据或共享职责/接口的根因，再修改依赖它的消费者；一般修改前后核对及现行正文同步沿lifecycle，不等收尾才更新有效依据。授权内局部修复可直接完成；跨模块重构拆成有界任务，复杂依赖写阶段计划。明确行为保持范围，需要补足回归保护时先补证据，按自然依赖点验证；产品含义、权限、不可逆迁移或发布决定按项目边界处理。扫描、修改和测试范围分别确定，命令及全量触发沿项目验证来源和verification。
6. **修改后遗漏核对。** 主要修改完成后，按实际增删改及职责、用途和消费者关系变化重核影响，同时检查原结论是否仍成立及是否产生新对象、新风险或新废弃物。包括内容未变但消费者已消失的旧代码/文件，不只核对修改文件或原发现清单；遗留判断和处置复用CH-01/CH-02/CH-06及目录清理方法。检查新增对象是否应进入相关专项覆盖，复用有效调查，共享结果只记录一次；不能按已查范围作出的结论，暂不作为后续依据，补查后更新原覆盖/发现及证据。新问题回到相应归因或修复，需要改变判断前提时返回前提核对；无关工作及未受影响证据继续使用。单次修复的相关影响及时核对，主要修改后的检查复用这些结果，仅补未覆盖或失效部分，不默认再扫全仓。
7. **最终收口。** 执行下方[收口的机械核对与语义核对](#收口的机械核对与语义核对)，再沿共同通过条件核对各项结论仍覆盖当前声明对象、本轮新增影响已有相应调查/处置依据及必需复验有效，更新现行文档和任务。治理体系回顾、复验或导览核对若触发实质修改，返回相关处置及修改后遗漏核对，再重验受影响部分；新产物按归属、消费者与保留要求核对，合法生成物不直接当废弃物。全面项目治理完成[项目导览页](#项目导览页)快照及页面核对后再交付。列明未完成、残余风险、后续归属和人的参与；范围内必需项不能转待办规避完成。预算用尽记录部分结果及下一动作，不降低标准；满足完成条件后停止追加可选检查。

### 收口的机械核对与语义核对

在拟声明本轮治理完成前执行，复用DC-04～06；文档更新、适用复验及全面治理导览核对完成后进行，不将早期扫描结果当成最终收口证据。普通局部任务只核对相关入口与义务，不因本节升级全面治理。

1. **固定身份与映射。** 从本轮授权和原任务确定声明对象、完成/部分结果范围、原始必需项来源及当前状态入口。明确需要表达“当前治理”的位置；“当前开发任务”“最近治理”“历史治理”不混用。不按文件名最大编号猜当前任务，不要求所有项目使用同一种命名或新建文件。
2. **实际执行机械核对。** 复用项目已有等效检查；缺少时调用[只读收口工具](cli.md#只读收口核对)，以原始路径、已有入口前缀和适用清单章节传参。核对失效本地引用、明确入口与任务身份、拟完成声明与可靠必需项状态。脚本模式复用assess；文档模式没有可靠结构时得到unknown，记录需要AI核对的具体项，不把它写成机械通过。保存实际命令/对象、结果及限制于原任务或已有证据附件；仅增加脚本/说明而未调用不算接入。失败先修正，未知先补依据或完成有证据的语义核对；依赖的完成声明保持待定。
3. **双向语义核对。** 从本轮发现及相关原任务/决定追到实际处置，范围内必需项须有有效关闭依据；仍影响后续工作的事项须能从现有状态/待办入口定位到原始来源，不要求复制所有历史事项。再从状态入口逐项回查原始依据，核对身份、范围、已实现/已验证/已交付，以及未验证、未实施、待决定、暂缓的区别。确认候选未被写成已授权任务，历史链接和有依据的暂缓/范围外项未被误列当前阻塞。只沿原发现清单检查不能证明清单完整，按实际变更及相关来源补查影响当前声明的遗漏；不承诺零遗漏。记录采用的来源、发现到处置/入口及入口到依据的关键对应和剩余边界，不另建事实台账。
4. **形成结论。** 机械与语义结论分别记录；无未闭合本轮必需项且证据有效才沿原流程完成。工具不能替AI签署语义结论，更不能替人批准产品、采用或发布。收口后相关来源改变，仅重核受影响项；范围外后续保留责任/触发，不自动授权执行。

## 覆盖与发现记录

在任务正文为所选专项的每个 ID 保留可追踪的结果，可用下表或等效记录并引用附件。共享调查、发现及证据只维护一次，关联多个 ID，不要求每项单独执行命令、重写报告或重复验证：

| 条目 ID | 检查对象与覆盖方式 | 依据及证据位置 | 结果与发现 ID | 限制 / 不适用依据 / 下一动作 |
|---|---|---|---|---|
| 专项 ID | 具体模块、文件或流程；工具扫描/关系核对/深入审查 | 当前规则、代码位置、命令结果或观察 | 已检查无发现 / 已检查有发现 / 不适用 / 未完成 | 事实与影响 |

“已检查无发现”只限已声明覆盖，不证明不存在所有问题。抽样必须说明选择依据及未深入区域；不能将抽样结果改称全项目逐项验证。发现至少记录位置、违反的依据或具体维护问题、影响、证据、已确认或待核实、优先级、建议及责任归属。猜测先记待核实。

- **阻塞问题**：已确认的数据/权限风险、关键功能或接口错误、关键验收不成立等；阻止依赖该结果的动作，在授权内修复或交由负责的人决定。
- **必需改进**：不构成立即故障，但违反当前规则或明显妨碍本阶段交付；列为范围内修复及复验要求。
- **可选改进**：收益有限的风格、未来优化等；可记录 backlog，附依据、责任与触发，不为清零而重构。

复核发现或建议时，分别核对事实是否成立、影响及适用范围、严重程度与建议必要性。用户质疑本身不是撤回依据；有局部反例时只修正受影响的结论，保留仍被证据支持的部分，并说明原结论、变更依据及影响。例如带日期/身份的导览正常落后，不能否定现行TESTING遗漏必需路径的发现；快照仍沿既定触发刷新，现行来源按原义务及时维护。

“已有原则”不能直接否定具体执行示例，须比较现有说明是否已足够、拟补示例是否更具体且有可检验用途；充分时复用，存在具名缺口时可局部补强。“候选收益未验证”限制已证明收益的声明，不自动否定优先验证的必要性；候选优先级按相关风险、预期用途及验证成本说明，不能冒充已证明收益。合理兼容、必要摘要或有理由的重复也不自动否定局部遗漏/冗余；复核按各自范围判断，不以一处合理用途整体撤回其他成立发现。

纯扫描任务以调查覆盖、发现清单、证据限制和后续归属为验收对象；例如，调查已完成而发现尚待修复时，可以交付扫描结果，但必须写“扫描完成，发现问题/修复待处理”，不能写“健康检查通过”。只有所有必需条目已检查或有成立的不适用依据、没有未完成项、阻塞与必需问题已处理且复验有效，才可在该范围声明通过。扫描状态、修复状态与项目验收分别记录；任务完成仍遵循原交付流程。

本清单是开发 AI 必须执行的约定。脚本模式的新正式专项扫描在任务正文使用唯一的 `harness-scan` 覆盖块，字段及命令见[扫描覆盖接口](cli.md#扫描覆盖记录)。它代替同内容覆盖表，不另建任务状态；详细调查和共享证据可作为附件引用。普通任务不创建覆盖块，历史记录不追补；文档模式仍可用上表或等效记录。

脚本读取现行专项ID，核对所选条目、引用文件、未完成项与结论是否相容；相关覆盖记录、专项正文或引用证据变化使该扫描任务旧RUN失效。AI仍负责适用判断、范围是否真实、检查是否执行、证据语义和修复复验。程序不能从普通任务文本判断是否漏建整个覆盖块，不能宣称不可绕过的扫描闸门；格式齐全、勾选和close通过均不能单独证明清单实际执行。检查方法、工具、实现和无依赖步骤顺序不由覆盖格式规定。

## 维护

流程或条目变更在新检查使用前同步入口、专项与适用项目映射；保持条目 ID 稳定，退役或替换说明对应关系，历史报告不改写。新增项目专用项必须保留共同底线。复查范围、证据或发现变化时更新任务，交接前更新 status。

## 成本与规则复查

### 阶段回顾与治理更新入口

可使用完整指令“使用 ai-sdlc，回顾本阶段执行过程，提炼经验并更新项目治理文件”，也可在已调用本 Skill 或已采纳相关项目规则的上下文中使用“治理体系更新”“治理规则更新”“阶段复盘”“经验沉淀”等短语。需要加载 Skill 时明确使用 `$ai-sdlc`；短语是任务意图，不是新增脚本命令，不改变显式调用策略。讨论这些词或询问能力不构成执行请求。

范围优先采用用户指定的阶段、任务或模块；未指定时从当前任务与状态入口定位最近阶段成果，并说明本次覆盖。范围无法确定且影响判断时再询问，不默认回顾全部历史。依据相关任务记录、实际差异、决定及验证结果，按下文复查受影响规则并保留有复用价值的经验；不因使用此入口自动升级为完整阶段健康检查。

“更新”请求包含当前范围内、已有授权允许的可逆文件维护；仅要求复盘或总结时先按原授权判断是否包含写入，明确只读时只报告。按各文件的现有职责更新唯一正文及必要入口，交付说明提炼结果、实际修改、依据和待决定事项。没有值得固化的经验时说明判断，可以不修改治理文件；不要求新增复盘报告模板。本入口补充主动维护，阶段触发时仍按下文执行，不以用户再次输入短语为前提。

### 主动复查

显式调用或项目已采纳相关规则的授权任务中，由开发 AI 主动执行，不要求用户提醒或填写统计表；没有运行中的 AI 或平台事件，不承诺后台定期检查。

- 漏检、误拦、反复提醒、重复返工出现时：在现有任务正文记录事实、原因、影响规则及最小改进。发现重复或结构性缺陷时，沿共享职责、调用、写入或生成关系追查同类入口与实现，检查边界混淆、重复维护等诱因，再决定修结构、补校验或增加提醒；不是每次事故都要新增规则。
- 实际观察到收益、负担或阶段复查需要时：在任务记录相关事实，可记提醒、返工、恢复或维护耗时，并注明来源。结论需要但缺少的数据列未知；普通收尾无此观察时不要求固定“未测”条目，不从测试数、代码行数或RUN耗时推算生产率。
- 阶段结束或模型、工具、规则重大变化时：仅复查受影响规则，区分必要结果约束与某次成功做法，后者按适用性保留为示例或移除；记录来源风险、执行位置、实际收益／误报、保留／修改／退役决定及下次复查触发。

一般可逆改进沿用授权；放宽验收、权限或数据保护先核对原规则与人的决定。无收益规则可以退役，但不能为获得通过而去掉必需检查。复杂取舍用现有决策模板；普通观察留任务正文，不新增成本台账作为每个项目的必建文件。

这些记录是复查材料，不因效率数据未知阻止工程完成。若事故修复是当前必需验收，则其回归证据仍须满足项目验证策略。

### 经验保留与复用

出现重复故障、有效诊断方法或可复用实现经验时，开发 AI 判断是否值得保留；有助于避免重复试错的失败路线也可保留。按复用需要说明问题特征、适用条件、有效做法或已排除路线、证据及已知限制；不从单次成功推断普遍有效，不要求每次收尾生成经验记录。

优先把经验落实为回归测试、诊断工具、清楚的错误信息或项目已有运行/验证说明；依赖情境判断的经验可留在任务或决定记录，并从相应项目入口提供可检索的引用。同一事实只维护一处，不另建默认知识库或重复台账。项目经验归项目；只有适合跨项目指导且有适用性依据的内容，才按现有授权维护为通用 Skill 规则，不能自动提升为所有项目的要求。

后续任务遇到相近问题或考虑采用历史做法时，沿项目入口、相关模块说明和任务/决定记录查找必要材料；核对当前版本、环境、约束及后续修正是否仍匹配。依据当前结论与风险选择必要验证，既不照搬旧结果，也不因读取经验重跑全部历史检查。条件变化或出现反例时，按证据修订适用范围或退役做法，更新现行入口并保留历史事实；可复用工具和记录随其职责维护，不以新增提醒代替修复根因。
